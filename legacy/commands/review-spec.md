# /review-spec

## Purpose
Run an **iterative review loop** between Codex CLI and Claude on a **high-level spec markdown file** (typically generated by the superpowers `writing-plans` / `brainstorming` skills). Each iteration: Codex critiques → Claude evaluates and applies accepted critiques → re-feed updated spec → repeat. Converges when the spec is good to ship.

**This is a SPEC review, NOT a code review.** Codex must NOT suggest code, file paths, function signatures, or implementation strategies. Critiques stay at the functional / non-functional requirement level.

**Ship it correctly the first time.** Plan the work to be done right and deployed — no bureaucracy, no red tape, no paranoid rollout choreography. Reject any critique that wants feature flags, env var gating, phased/dark/canary rollouts, A/B harnesses, or backwards-compat shims unless the spec's stated goals explicitly require them.

**Claude's role:** You are the human-in-the-loop reviewer of Codex's review. Push back. Don't rubber-stamp every finding — reject anything that drifts into implementation, repeats what the spec already says, adds rollout-paranoia NFRs, or is pure bikeshedding. The goal is a *better spec*, not a longer one.

**Loop semantics — exit `STATUS=CLEAN` when ANY of:**
1. Codex returns zero findings (spec is solid at the requirement level)
2. Every finding this iteration is rejected as worthless (drift, bikeshedding, invented requirements)
3. Findings flip-flop with prior iterations (Codex contradicts a critique it already made and got applied) — loop has converged

## Contract
**Inputs:**
- `$1` — path to the spec markdown file (**optional** — if omitted, resolve from session context: see Step 1)
- `--fast` — shorthand that maps to `--enable fast_mode` on the codex invocation for quicker (lower-fidelity) responses. NOT a literal codex flag named `--fast`
- `--model MODEL` — Codex model override (default: Codex's own configured default — the latest state-of-the-art model; never pin a specific version)

**Outputs:** `STATUS=<CLEAN|FAIL> SPEC=<resolved-path> ITERATIONS=<N> ACCEPTED=<N> REJECTED=<N> [ERROR="..."]`

## Instructions

**First, invoke the `codex-cli` skill** (via the Skill tool) — it is the source of truth for the reliable Codex CLI invocation recipe. Follow it for every `codex` call below; if its guidance ever conflicts with this command, the skill wins.

1. **Resolve the spec path:**
   - If `$1` is provided, use it directly. Skip to validation
   - If `$1` is omitted, **resolve the most recent spec from the current session's context/history** in this priority order:
     1. The last spec MD file the user pasted, referenced by path, or asked you to read in this conversation
     2. The most recent file matching common spec paths created/edited this session — typical superpowers locations: `specs/**/*.md`, `.specs/**/*.md`, `docs/specs/**/*.md`, `requirements/**/*.md`, or any `*-spec.md` / `*-requirements.md` / `*-brief.md` file you wrote or edited via Write/Edit. **Skip plan files** (`plans/**`, `*-plan.md`, `*-implementation*.md`) — those belong to `/review-implementation-plan`
     3. Fall back to `git status` + `git diff --name-only HEAD` for modified `*.md` files in spec-like directories
   - **State the resolved path to the user** before proceeding ("Reviewing: `<path>` — proceeding"). If multiple plausible candidates exist, pick the most recently modified and mention the runners-up briefly so the user can correct
   - If the candidate file is clearly an implementation plan (contains code blocks, schemas, file paths, function signatures), warn the user and suggest `/review-implementation-plan` instead
   - If nothing resolves, fail with `STATUS=FAIL ERROR="no spec path provided and none found in session context"` and ask the user to pass one explicitly

2. **Validate inputs:**
   - Confirm `codex` CLI is installed: `command -v codex` (fail with install hint if missing)
   - Confirm spec file exists and is readable: `test -f "$SPEC_PATH"`
   - Confirm it's a markdown file (`.md` extension); warn if not but allow override
   - Parse `--fast` flag (shorthand, NOT a literal codex flag): when set, add `--enable fast_mode` to the `codex` invocation
   - Parse `--model` (default: current Codex default)
   - Initialize history ledger: `> /tmp/review-spec-history.txt` (truncate fresh each command run)

3. **Loop: review → evaluate → apply → repeat.** For each iteration `N` starting at 1:

   **a. Invoke Codex for spec review.**

   Write the JSON Schema once before the loop (enforces the output shape so the `-o` file is parseable JSON — no JSONL, no fences):
   ```bash
   cat > /tmp/review-spec-schema.json <<'EOF'
   {
     "type": "object", "additionalProperties": false,
     "required": ["critiques", "summary"],
     "properties": {
       "critiques": {
         "type": "array",
         "items": {
           "type": "object", "additionalProperties": false,
           "required": ["severity", "category", "section", "issue", "question_for_author"],
           "properties": {
             "severity": {"type": "string", "enum": ["high", "medium", "low"]},
             "category": {"type": "string", "enum": ["logic", "assumption", "edge-case", "ambiguity", "nfr-gap", "stakeholder", "scope", "conflict"]},
             "section": {"type": "string"},
             "issue": {"type": "string"},
             "question_for_author": {"type": "string"}
           }
         }
       },
       "summary": {"type": "string"}
     }
   }
   EOF
   ```
   ```bash
   # Codex CLI has NO --prompt/--input-file flags. The prompt is the positional argument;
   # the document is piped via stdin (Codex appends it to the prompt as a <stdin> block).
   # --skip-git-repo-check is required when CWD is not a trusted git repo (hard error otherwise).
   # Use --output-schema + -o (NOT --json): the -o file is then schema-conforming JSON, read it directly.
   # --fast maps to --enable fast_mode (shorthand, not a literal flag). Pass --model only when overridden.
   codex exec ${FAST:+--enable fast_mode} --skip-git-repo-check ${MODEL:+--model "$MODEL"} \
     --output-schema /tmp/review-spec-schema.json -o /tmp/review-spec-output.json \
     "You are a senior product engineer reviewing a HIGH-LEVEL SPECIFICATION document — not an implementation plan. The spec describes WHAT a system should do at the requirement level (functional + non-functional), NOT HOW to build it. The spec document is provided in the <stdin> block.

   Your job: surface requirement-level critiques only.

   IN SCOPE:
   - Logical errors or contradictions in the requirements
   - Faulty or unstated assumptions the spec relies on
   - Missing edge cases (failure modes, concurrency, scale boundaries, empty/null states, permission boundaries, partial-failure recovery)
   - Ambiguous or under-specified requirements
   - Missing non-functional requirements (performance, security, observability, accessibility, latency budgets, data retention, compliance, error budgets) when relevant
   - Stakeholder/persona gaps — whose needs aren't represented?
   - Boundary/scope ambiguity — what's in vs out
   - Conflicts with stated goals or success criteria

   STRICTLY OUT OF SCOPE — DO NOT MENTION:
   - Code, file paths, function names, class structures, API signatures
   - Library/framework recommendations
   - Implementation strategies, algorithms, data structures
   - Testing strategies (unless the spec itself specifies them)
   - Wording/grammar/formatting nitpicks
   - Rollout-paranoia requirements: feature flags, env var toggles, phased/canary/dark launches, A/B tests, backwards-compat shims, kill switches — unless the spec's stated goals explicitly demand them. Assume the work ships correctly on merge
   - Bureaucratic process additions: sign-offs, review boards, change-management gates, runbook ceremonies beyond what's actually needed for the system to be safe
   - Anything that requires inventing new requirements rather than improving stated ones

   Return strict JSON:
   {
     \"critiques\": [
       {
         \"severity\": \"high|medium|low\",
         \"category\": \"logic|assumption|edge-case|ambiguity|nfr-gap|stakeholder|scope|conflict\",
         \"section\": \"<spec section/heading reference>\",
         \"issue\": \"<one-paragraph description of the requirement-level problem>\",
         \"question_for_author\": \"<the clarifying question this raises>\"
       }
     ],
     \"summary\": \"<one-line verdict on spec readiness>\"
   }

   Return an empty critiques array if the spec is genuinely solid at the requirement level. Do NOT fabricate critiques to fill space." \
     < "$SPEC_PATH" 2>/dev/null
   ```

   Tip: write the prompt once to `/tmp/review-spec-prompt.txt` and pass `"$(cat /tmp/review-spec-prompt.txt)"` as the positional argument — avoids re-sending the giant inline string every iteration.

   **Parsing the output:** Read `/tmp/review-spec-output.json` directly — `--output-schema` guarantees it is one schema-conforming JSON object (no JSONL events, no markdown fences). `JSON.parse` it. Fail closed (`STATUS=FAIL ERROR="invalid codex output"`) if the file is missing or unparseable.

   **b. Convergence check #1 — empty critiques:**
   - If `critiques` is empty → exit loop with `STATUS=CLEAN`, print Codex's summary, done

   **c. Push back, don't rubber-stamp.** For each critique, Claude decides accept or reject:
   - **Reject** critiques that:
     - Stray into implementation (code, file paths, libraries, algorithms, schemas)
     - Repeat what the spec already explicitly states
     - Are wording/grammar/formatting nitpicks
     - Invent requirements not implied by the spec's stated goals
     - Add rollout-paranoia: feature flags, env var gating, phased/dark/canary launches, A/B harnesses, backwards-compat shims, kill switches — unless the spec's stated goals explicitly demand them
     - Add bureaucratic process (sign-off gates, review boards, change-management ceremony) the system doesn't actually need
     - Are pure bikeshedding ("consider adding more detail" with no specific gap)
   - **Accept** critiques that genuinely improve requirement-level clarity, completeness, or correctness

   **d. Convergence check #2 — all rejected:**
   - If every critique this iteration was rejected → exit loop with `STATUS=CLEAN`, log "all-rejected: <reasons>" to history, print summary

   **e. Convergence check #3 — flip-flop detection:**
   - Cross-check accepted critiques against `/tmp/review-spec-history.txt` (entries from prior iterations). A flip-flop = Codex now suggesting to revert, contradict, or invert a change applied in an earlier iteration (e.g., earlier said "make X stricter," now says "X is too strict"; or earlier added requirement Y, now says "remove Y")
   - If ALL accepted critiques are flip-flops → exit loop with `STATUS=CLEAN`, log the contradiction to history, surface it to the user
   - If SOME critiques are flip-flops, drop just those (treat as rejected) and continue with the rest

   **f. Apply accepted critiques to the spec file:**
   - Use Edit tool to revise the spec MD file in place — clarify ambiguities, add missing edge cases, resolve contradictions, fill NFR gaps, etc. Each edit at the requirement level only — never inject code, schemas, or implementation language
   - Keep edits minimal and faithful to the original voice; don't bloat the spec

   **g. Append to history ledger:**
   - One line per iteration to `/tmp/review-spec-history.txt`: `iter=<N> accepted=<count> rejected=<count> sections=[<list>] summary="<short>"`

   **g2. Capture deferral candidates.**
   - When you reject a critique because it would *complicate the current spec / task / Linear issue* but is genuinely worth doing later (a separable concern, a "while you're here" the spec should not absorb, a related-but-orthogonal gap), append a JSON line to `/tmp/review-spec-followups.jsonl`:
     `{"iter": <N>, "title": "<short imperative title>", "rationale": "<1–2 sentences: what + why it's worth doing later>", "source_section": "<spec section>", "category": "<original critique category>"}`
   - Do NOT capture pure-noise rejections (drift, bikeshedding, invented requirements, rollout paranoia, bureaucracy). Only capture rejections that are real-but-out-of-scope work
   - De-dup against existing lines before appending

   **h. Continue loop:**
   - Re-feed the updated spec to Codex (return to step 3a)
   - No iteration cap — convergence is the only stopping criterion (along with FAIL conditions)

4. **Final output:**
   - Print `STATUS=CLEAN SPEC=<path> ITERATIONS=<N> ACCEPTED=<total> REJECTED=<total>`
   - Print Codex's final one-line summary verdict
   - Print a brief diff summary of what changed across all iterations (sections touched, types of gaps closed)
   - If exited via flip-flop or all-rejected, explain that to the user so they know why the loop stopped early
   - Do NOT push, commit, or create new files. The spec file itself was edited per iteration; the user decides whether to commit

5. **Propose follow-up Linear issues (gated on user approval):**
   - Read `/tmp/review-spec-followups.jsonl`. If empty, print `Follow-ups: none` and stop
   - Print a numbered list to the user — each item: `title`, `rationale`, `source_section`. Order by perceived value (high → low). Cap at the 5–10 most worthwhile; mention the count of any extras
   - Ask the user explicitly: *"Create these as Linear issues assigned to khai@promptarmor.com? Reply with the numbers to create (e.g. `1,3,4`), `all`, or `none`. You can also edit titles inline."* — wait for the response. **Do not create any issue without approval.**
   - For each approved item, create one Linear issue via `mcp__claude_ai_Linear__save_issue`:
     - `assignee`: resolve `khai@promptarmor.com` via `mcp__claude_ai_Linear__list_users` (filter by email) — REQUIRED. If lookup fails, abort that issue and report the error; do not silently drop the assignee
     - `title`: from the follow-up entry (or the user's edited version)
     - `description`: the `rationale` plus a `Source:` line referencing the spec file path and section, plus an `Origin:` line noting it was deferred from a `/review-spec` run
     - `team`: best-effort default — look up the user's most recently active team via `mcp__claude_ai_Linear__list_teams` and pick the one most issues are filed against; if ambiguous, ask the user once for the team key, then reuse it for the rest of this batch
     - `priority`: default `3` (Medium); bump to `2` (High) if the original critique severity was `high`
     - `state`: default to the team's `Backlog` (or `Triage` if Backlog doesn't exist)
     - `labels`: omit — user will tag manually
   - After creation, print each issue's identifier and URL. Truncate `/tmp/review-spec-followups.jsonl` once issues are filed
   - If the user replies `none`, leave the file intact so they can revisit later

## Constraints
- **Spec-level only** — reject any Codex output that names code, files, functions, libraries, schemas, or algorithms
- **Ship-it-right-first-time framing** — reject rollout choreography (flags, env gating, phased launches, A/B, kill switches, compat shims) and bureaucratic gates unless the spec's stated goals explicitly require them
- **Push back on Codex** — Claude is the human-in-the-loop, not a rubber stamp. Skip drift/nitpicks/invented requirements/rollout-paranoia and note the rejection
- **Loop until convergence** — exit CLEAN only when: zero findings, all rejected, or all flip-flops. No iteration cap
- **Edit the spec in place** — Claude applies accepted critiques via Edit tool per iteration. No commits, no pushes
- **Track history** — maintain `/tmp/review-spec-history.txt` for flip-flop detection across iterations
- **Capture deferrals, not noise** — write only real-but-out-of-scope rejections to `/tmp/review-spec-followups.jsonl`. Never capture drift, bikeshedding, rollout paranoia, or bureaucracy
- **Linear issues require explicit approval** — never create Linear issues without the user replying with which numbers to file. Assignee `khai@promptarmor.com` is mandatory; team / priority / state get reasonable defaults; labels are left blank
- **Fail closed** on ambiguous Codex output (non-JSON, truncated): `STATUS=FAIL ERROR="invalid codex output"`
- **Faithful edits** — don't bloat the spec; preserve original voice and structure when revising
