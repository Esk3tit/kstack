# /review-implementation-plan

## Purpose
Run an **iterative review loop** between Codex CLI and Claude on an **implementation plan markdown file** (typically generated by the superpowers `writing-plans` / `executing-plans` skills). Each iteration: Codex critiques → Claude evaluates and applies accepted critiques → re-feed updated plan → repeat. Converges when the plan is good to execute.

**This is an IMPLEMENTATION PLAN review.** Unlike `/review-spec`, Codex IS allowed and encouraged to critique concrete code details: function signatures, schemas, SQL, algorithms, data structures, package choices, library APIs, migration steps, query plans. Go deep on logical errors and edge cases.

**Ship it correctly the first time, then deploy.** Plan each Linear issue / task to be done right and merged — no feature flags, no env var gating, no phased/dark/canary rollouts, no A/B harnesses, no backwards-compat shims, no kill switches, no `if (NEW_BEHAVIOR_ENABLED)` toggles. Just change the code. The only exceptions: (a) the plan's own goals explicitly require gradual rollout (e.g., a migration that *cannot* be atomic), or (b) the change touches a true blast-radius surface (billing, auth, data destruction) where staged exposure is genuinely warranted. Default = ship it.

**Keep it simple. Prefer elegant solutions.** Codex must NOT pile on style nitpicks, formatting, naming bikeshedding, premature abstractions, defensive code for impossible states, useless tests, "while you're here" refactors, or rollout paranoia. Actively look for simpler approaches — fewer lines, fewer branches, fewer abstractions, fewer moving parts. The goal is a *correct, minimal, elegant* plan — not a longer one.

**Comments stay minimal.** Reject planned code that adds multi-paragraph docstrings, narrative comment blocks, or comments explaining WHAT the code does (well-named identifiers cover that). Allow comments only when they convey WHY — a non-obvious constraint, a subtle invariant, a workaround for a specific bug. Cap at 2 lines. No `// Phase 2`, `// per code review`, `// PR #1234`, `// removed X` markers — those rot.

**Claude's role:** You are the human-in-the-loop reviewer of Codex's review. Push back. Don't rubber-stamp every finding — reject anything that's pure bikeshedding, adds bloat, suggests useless tests, adds rollout paranoia, bloats comments, or invents requirements not implied by the plan.

**Loop semantics — exit `STATUS=CLEAN` when ANY of:**
1. Codex returns zero findings (plan is good to execute)
2. Every finding this iteration is rejected as worthless (style nits, bloat, useless tests, drift)
3. Findings flip-flop with prior iterations (Codex contradicts a critique it already made and got applied) — loop has converged

## Contract
**Inputs:**
- `$1` — path to the plan markdown file (**optional** — if omitted, resolve from session context: see Step 1)
- `--fast` — shorthand that maps to `--enable fast_mode` on the codex invocation for quicker (lower-fidelity) responses. NOT a literal codex flag named `--fast`
- `--model MODEL` — Codex model override (default: Codex's own configured default — the latest state-of-the-art model; never pin a specific version)

**Outputs:** `STATUS=<CLEAN|FAIL> PLAN=<resolved-path> ITERATIONS=<N> ACCEPTED=<N> REJECTED=<N> [ERROR="..."]`

## Instructions

1. **Resolve the plan path:**
   - If `$1` is provided, use it directly. Skip to validation
   - If `$1` is omitted, **resolve the most recent implementation plan from the current session's context/history**, prioritizing the superpowers `writing-plans` / `executing-plans` skill output:
     1. The last plan MD file the user pasted, referenced by path, or asked you to read in this conversation
     2. The most recent file in superpowers-typical plan locations created/edited this session: `plans/**/*.md`, `.plans/**/*.md`, `docs/plans/**/*.md`, `specs/**/implementation*.md`, or any `*-plan.md` / `*-implementation*.md` you wrote/edited via Write/Edit. **Skip pure spec files** (`*-spec.md`, `*-requirements.md`, `*-brief.md`, files in `requirements/**`) — those belong to `/review-spec`
     3. Fall back to `git status` + `git diff --name-only HEAD` for modified `*.md` files in plan-like directories
   - **State the resolved path to the user** before proceeding ("Reviewing: `<path>` — proceeding"). If multiple plausible candidates exist, pick the most recently modified and mention runners-up briefly so the user can correct
   - If the candidate file is clearly a high-level spec (no code blocks, no schemas, no function signatures, just functional/non-functional requirements), warn the user and suggest `/review-spec` instead
   - If nothing resolves, fail with `STATUS=FAIL ERROR="no plan path provided and none found in session context"` and ask the user to pass one explicitly

2. **Validate inputs:**
   - Confirm `codex` CLI is installed: `command -v codex` (fail with install hint if missing)
   - Confirm plan file exists and is readable: `test -f "$PLAN_PATH"`
   - Confirm it's a markdown file (`.md` extension); warn if not but allow override
   - Parse `--fast` flag (shorthand, NOT a literal codex flag): when set, add `--enable fast_mode` to the `codex` invocation
   - Parse `--model` (default: current Codex default)
   - Initialize history ledger: `> /tmp/review-implementation-plan-history.txt` (truncate fresh each command run)

3. **Loop: review → evaluate → apply → repeat.** For each iteration `N` starting at 1:

   **a. Invoke Codex for plan review.**

   Write the JSON Schema once before the loop (enforces the output shape so the `-o` file is parseable JSON — no JSONL, no fences):
   ```bash
   cat > /tmp/review-implementation-plan-schema.json <<'EOF'
   {
     "type": "object", "additionalProperties": false,
     "required": ["critiques", "summary"],
     "properties": {
       "critiques": {
         "type": "array",
         "items": {
           "type": "object", "additionalProperties": false,
           "required": ["severity", "category", "section", "issue", "suggested_change"],
           "properties": {
             "severity": {"type": "string", "enum": ["high", "medium", "low"]},
             "category": {"type": "string", "enum": ["logic", "edge-case", "schema", "algorithm", "tech-choice", "api-design", "concurrency", "security", "observability", "contradiction", "simplicity"]},
             "section": {"type": "string"},
             "issue": {"type": "string"},
             "suggested_change": {"type": "string"}
           }
         }
       },
       "summary": {"type": "string"}
     }
   }
   EOF
   ```
   ```bash
   # Codex CLI has NO --prompt/--input-file flags. The prompt is the positional argument;
   # the document is piped via stdin (Codex appends it to the prompt as a <stdin> block).
   # --skip-git-repo-check is required when CWD is not a trusted git repo (hard error otherwise).
   # Use --output-schema + -o (NOT --json): the -o file is then schema-conforming JSON, read it directly.
   # --fast maps to --enable fast_mode (shorthand, not a literal flag). Pass --model only when overridden.
   codex exec ${FAST:+--enable fast_mode} --skip-git-repo-check ${MODEL:+--model "$MODEL"} \
     --output-schema /tmp/review-implementation-plan-schema.json -o /tmp/review-implementation-plan-output.json \
     "You are a senior engineer reviewing a CONCRETE IMPLEMENTATION PLAN — code, schemas, algorithms, packages, migrations, the works. Go deep on correctness. The plan document is provided in the <stdin> block.

   IN SCOPE — critique aggressively at this level:
   - Logical errors in proposed code, control flow, or state machines
   - Edge cases the plan doesn't handle: empty/null/zero, max bounds, concurrency, partial failure, retries, idempotency, ordering, race conditions, transaction boundaries, off-by-one, timezone/DST, unicode boundaries, duplicate inputs, permission boundaries
   - Schema / migration issues: NULL vs NOT NULL, defaults, locks during DDL, online-migration safety, index gaps, constraint conflicts, FK cascade surprises, data backfill correctness
   - Algorithm / data-structure mismatches: O(N) where O(log N) is needed, unbounded memory growth, N+1 queries, missing pagination
   - Technology / package mismatches: wrong library for the job, deprecated APIs, version compatibility, missing required deps, license issues
   - API design flaws at the contract level: wrong status codes, missing validation, inconsistent error shapes, missing pagination/cursoring, breaking-change risk
   - Concurrency / scale boundaries: thread safety, queue backpressure, rate limits, timeout cascades, retry storms, fan-out problems
   - Security / auth gaps in the proposed implementation: missing authz checks, leaked secrets, SSRF, SQL injection vectors, untrusted input flowing into shell/eval
   - Observability gaps: missing logs/metrics/traces at decision points where production debugging will fail
   - Contradictions between sections of the plan
   - Code simplicity: spots where a smaller, more direct, more elegant solution exists — collapsing branches, removing intermediate state, using a stdlib primitive instead of a hand-rolled helper, deleting an abstraction that only has one caller. Suggest the simpler form concretely

   STRICTLY OUT OF SCOPE — do NOT include:
   - Style/formatting/naming nitpicks (let the linter handle it)
   - Premature abstractions or 'extract this into a helper'
   - Defensive code for impossible states
   - Bloated fallbacks or 'in case' error handling
   - 'While you're here' refactors of code not touched by the plan
   - Useless tests: tests that just assert the new code was added, tests that verify old behavior is no longer present (instead of testing real behavior), tests for trivial getters/setters, tests that re-implement the function under test, mock-the-world tests
   - Rollout paranoia: feature flags, env var gating, phased / dark / canary launches, A/B harnesses, kill switches, backwards-compat shims, `if (NEW_BEHAVIOR)` toggles. Assume the change ships correctly on merge. The only exception: the plan itself explicitly requires gradual rollout, or the change touches a true high-blast-radius surface (billing, auth, irreversible data ops) where staged exposure is genuinely warranted
   - Bureaucratic process additions: extra sign-offs, review boards, change-management gates, runbook ceremonies beyond what the system actually needs
   - Comment bloat: multi-paragraph docstrings, narrative comment blocks, comments explaining WHAT the code does, references to phases / tasks / Linear issues / PR numbers / iteration numbers / review findings. Allow ≤2-line comments only when conveying WHY (non-obvious constraint, subtle invariant, bug workaround)
   - 'Add a comment explaining X' unless an invariant is genuinely non-obvious and the comment stays within 2 lines
   - Wording / grammar / docstring tweaks
   - Anything that adds complexity without fixing a real correctness or safety problem

   Return strict JSON:
   {
     \"critiques\": [
       {
         \"severity\": \"high|medium|low\",
         \"category\": \"logic|edge-case|schema|algorithm|tech-choice|api-design|concurrency|security|observability|contradiction|simplicity\",
         \"section\": \"<plan section/heading or step reference>\",
         \"issue\": \"<concrete description of the correctness/safety/simplicity problem>\",
         \"suggested_change\": \"<smallest correct change to the plan — no bloat, no rollout gating, no comment padding>\"
       }
     ],
     \"summary\": \"<one-line verdict on plan readiness to execute>\"
   }

   Return an empty critiques array if the plan is genuinely solid. Do NOT fabricate critiques to fill space. Prefer 3 sharp findings over 15 mediocre ones." \
     < "$PLAN_PATH" 2>/dev/null
   ```

   Tip: write the prompt once to `/tmp/review-implementation-plan-prompt.txt` and pass `"$(cat /tmp/review-implementation-plan-prompt.txt)"` as the positional argument — avoids re-sending the giant inline string every iteration.

   **Parsing the output:** Read `/tmp/review-implementation-plan-output.json` directly — `--output-schema` guarantees it is one schema-conforming JSON object (no JSONL events, no markdown fences). `JSON.parse` it. Fail closed (`STATUS=FAIL ERROR="invalid codex output"`) if the file is missing or unparseable.

   **b. Convergence check #1 — empty critiques:**
   - If `critiques` is empty → exit loop with `STATUS=CLEAN`, print Codex's summary, done

   **c. Push back, don't rubber-stamp.** For each critique, Claude decides accept or reject:
   - **Reject** critiques that:
     - Are pure style/naming/formatting nitpicks
     - Suggest premature abstractions or helper extractions
     - Add defensive code for impossible states or bloated fallbacks
     - Suggest useless tests (asserting code was added, verifying old behavior absent rather than new behavior present, trivial getter/setter tests, mock-the-world tests, tests that re-implement the function)
     - Add rollout paranoia — feature flags, env var gates, phased / dark / canary launches, A/B harnesses, kill switches, `if (NEW)` toggles, backwards-compat shims. Accept ONLY if the plan's stated goals require gradual rollout or the change touches a true high-blast-radius surface (billing, auth, irreversible data)
     - Add bureaucratic process (extra sign-offs, change-management gates, runbook ceremonies) the system doesn't actually need
     - Add comment bloat — multi-paragraph docstrings, narrative blocks, comments restating WHAT the code does, references to phases / tasks / Linear / PRs / iterations / review findings, or any single comment longer than 2 lines
     - Push 'while you're here' refactors out of scope
     - Are contradicted by another part of the plan that Codex didn't notice
     - Invent requirements the plan doesn't imply
   - **Accept** critiques that fix real correctness/safety/edge-case problems with the smallest viable change, OR that genuinely simplify the proposed code (fewer lines, fewer branches, fewer abstractions) without losing correctness

   **d. Convergence check #2 — all rejected:**
   - If every critique this iteration was rejected → exit loop with `STATUS=CLEAN`, log "all-rejected: <reasons>" to history, print summary

   **e. Convergence check #3 — flip-flop detection:**
   - Cross-check accepted critiques against `/tmp/review-implementation-plan-history.txt` (entries from prior iterations). A flip-flop = Codex now suggesting to revert, contradict, or invert a change applied in an earlier iteration (e.g., earlier said "add a transaction here," now says "remove the transaction"; or earlier said "use library X," now says "X is the wrong choice")
   - If ALL accepted critiques are flip-flops → exit loop with `STATUS=CLEAN`, log the contradiction to history, surface it to the user
   - If SOME critiques are flip-flops, drop just those (treat as rejected) and continue with the rest

   **f. Apply accepted critiques to the plan file:**
   - Use Edit tool to revise the plan MD file in place — fix logic errors, add missing edge-case handling, correct schema/migration steps, swap bad tech/package choices, tighten API contracts, close security/observability gaps. Apply the **smallest correct change** per critique
   - Do NOT bloat the plan with extra defensive code, useless tests, or comments. Edits should remove problems, not pile on safety theater

   **g. Append to history ledger:**
   - One line per iteration to `/tmp/review-implementation-plan-history.txt`: `iter=<N> accepted=<count> rejected=<count> sections=[<list>] categories=[<list>] summary="<short>"`

   **g2. Capture deferral candidates.**
   - When you reject a critique because it would *complicate the current task / Linear issue* but is genuinely worth doing later (a "while you're here" the current plan should not absorb, a separable refactor, an orthogonal fix, follow-on observability/perf/hardening work, a tech-debt cleanup the change uncovered), append a JSON line to `/tmp/review-implementation-plan-followups.jsonl`:
     `{"iter": <N>, "title": "<short imperative title>", "rationale": "<1–2 sentences: what + why it's worth doing later>", "source_section": "<plan section/step>", "category": "<original critique category>", "severity": "<high|medium|low>"}`
   - Do NOT capture pure-noise rejections (style nits, premature abstraction, defensive bloat, useless tests, rollout paranoia, comment bloat, invented requirements). Only capture rejections that are real-but-out-of-scope work
   - De-dup against existing lines before appending

   **h. Continue loop:**
   - Re-feed the updated plan to Codex (return to step 3a)
   - No iteration cap — convergence is the only stopping criterion (along with FAIL conditions)

4. **Final output:**
   - Print `STATUS=CLEAN PLAN=<path> ITERATIONS=<N> ACCEPTED=<total> REJECTED=<total>`
   - Print Codex's final one-line summary verdict
   - Print a brief diff summary of what changed across all iterations (sections touched, categories of issues fixed)
   - If exited via flip-flop or all-rejected, explain that to the user so they know why the loop stopped early
   - Do NOT push, commit, or create new files. The plan file itself was edited per iteration; the user decides whether to commit

5. **Propose follow-up Linear issues (gated on user approval):**
   - Read `/tmp/review-implementation-plan-followups.jsonl`. If empty, print `Follow-ups: none` and stop
   - Print a numbered list to the user — each item: `title`, `rationale`, `source_section`, original `severity`. Order by severity (high → low), then by perceived value. Cap at the 5–10 most worthwhile; mention the count of any extras
   - Ask the user explicitly: *"Create these as Linear issues assigned to khai@promptarmor.com? Reply with the numbers to create (e.g. `1,3,4`), `all`, or `none`. You can also edit titles inline."* — wait for the response. **Do not create any issue without approval.**
   - For each approved item, create one Linear issue via `mcp__claude_ai_Linear__save_issue`:
     - `assignee`: resolve `khai@promptarmor.com` via `mcp__claude_ai_Linear__list_users` (filter by email) — REQUIRED. If lookup fails, abort that issue and report the error; do not silently drop the assignee
     - `title`: from the follow-up entry (or the user's edited version)
     - `description`: the `rationale` plus a `Source:` line referencing the plan file path and section/step, plus an `Origin:` line noting it was deferred from a `/review-implementation-plan` run
     - `team`: best-effort default — look up the user's most recently active team via `mcp__claude_ai_Linear__list_teams` and pick the one most issues are filed against; if ambiguous, ask the user once for the team key, then reuse it for the rest of this batch
     - `priority`: default `3` (Medium); bump to `2` (High) if the original critique severity was `high`; drop to `4` (Low) if severity was `low`
     - `state`: default to the team's `Backlog` (or `Triage` if Backlog doesn't exist)
     - `labels`: omit — user will tag manually
   - After creation, print each issue's identifier and URL. Truncate `/tmp/review-implementation-plan-followups.jsonl` once issues are filed
   - If the user replies `none`, leave the file intact so they can revisit later

## Constraints
- **Implementation level allowed** — code, schemas, algorithms, packages, migrations, queries are all fair game (unlike `/review-spec`)
- **Ship it right the first time** — reject feature flags, env var gates, phased / dark / canary launches, A/B harnesses, kill switches, and backwards-compat shims by default. Each task should land correct and deployed. Exceptions: the plan itself requires gradual rollout, or the change touches billing / auth / irreversible data
- **Keep it simple, hunt for elegance** — reject style nits, premature abstractions, defensive bloat, useless tests, 'while you're here' churn, and rollout paranoia. Accept critiques that genuinely shrink the code (fewer lines, branches, abstractions, moving parts) without losing correctness
- **Cover edge cases** — empty/null/zero, max bounds, concurrency, partial failure, retries, idempotency, ordering, race conditions, transaction boundaries, off-by-one, timezone/DST, unicode, duplicates, permission boundaries. These stay firmly in scope
- **Comments minimal** — reject planned code with multi-paragraph docstrings, narrative blocks, WHAT-explaining comments, or task/PR/Linear/phase/iteration references. Allow ≤2-line comments only when they convey WHY (non-obvious constraint, subtle invariant, bug workaround)
- **No useless tests** — explicitly reject tests that assert code was added, tests that verify old behavior is absent (instead of new behavior is correct), trivial getter tests, mock-the-world tests, or tests that re-implement the function under test
- **Push back on Codex** — Claude is the human-in-the-loop, not a rubber stamp. Skip drift/bloat/invented requirements/rollout-paranoia/comment-bloat and note the rejection
- **Loop until convergence** — exit CLEAN only when: zero findings, all rejected, or all flip-flops. No iteration cap
- **Edit the plan in place** — Claude applies accepted critiques via Edit tool per iteration. No commits, no pushes
- **Track history** — maintain `/tmp/review-implementation-plan-history.txt` for flip-flop detection across iterations
- **Capture deferrals, not noise** — write only real-but-out-of-scope rejections to `/tmp/review-implementation-plan-followups.jsonl`. Never capture style nits, premature abstractions, defensive bloat, useless tests, rollout paranoia, comment bloat, or invented requirements
- **Linear issues require explicit approval** — never create Linear issues without the user replying with which numbers to file. Assignee `khai@promptarmor.com` is mandatory; team / priority / state get reasonable defaults; labels are left blank
- **Smallest correct change** — apply minimal edits per critique. Don't bloat the plan
- **Fail closed** on ambiguous Codex output (non-JSON, truncated): `STATUS=FAIL ERROR="invalid codex output"`
