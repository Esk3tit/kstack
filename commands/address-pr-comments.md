# /address-pr-comments

Inside T3, follow its injected orchestration instructions instead of native CLI transport. Use a bounded handful of independent fixers and the existing fan-out approval rule; dependent work stays serial.

Address every **open finding** on a PR, both unresolved threads and review-body items: judge each one, fix what's valid, push back on what isn't, answer every finding, resolve its thread. Then loop — push, let the reviewers re-review, repeat — until the PR converges.

**Idempotent.** Each pass works only the unresolved threads whose last comment is not ours and the reviews whose body items we have not answered yet, so re-running is always safe.

- `$1` — PR number (optional; defaults to the current branch's PR)
- `--once` — run a single pass and stop, instead of looping to convergence

**GitHub via `gh-axi`.** Run every GitHub operation here through `gh-axi` (invoke `npx -y gh-axi …`) — the agent-ergonomic wrapper with token-efficient output; fall back to plain `gh` only if it's unavailable. It needs an authenticated `gh` underneath. Key forms: `pr view [<n>] --comments --reviews`, `pr checks <n>`, and `api [METHOD] <path>` — raw REST plus `api POST /graphql --field query=…` for thread resolution and replies.

## Reviewers vs. deploys

Classify every check and comment source by name into exactly one bucket — the loop gates on **reviewers** and is blind to **deploys**:

- **Reviewers** (gate the loop): code-review bots/agents — Gemini Code Assist, CodeRabbit, Greptile, Codex / cloud PR review, Cursor Bugbot, Sentry — plus lint/format and test check-runs — Prettier, ESLint, Ruff, pytest, vitest, Playwright. A failing lint or test is a real finding to fix.
- **Deploys** (never wait on, never gate): CI/CD pipeline jobs — preview-environment deployments, build/publish, Docker image builds, infra provisioning. A pending or red deploy never blocks convergence and is never a finding.

## Review-body items

A **review-body item** is a finding a bot writes inside a review's body instead of as a thread. CodeRabbit puts its "Nitpick comments (N)" and "Outside diff range comments (N)" there, in collapsed `<details>` blocks, each naming a file and line range; other bots do the same under their own headings. They never appear in `reviewThreads`, so read every review's body: `gh-axi api 'repos/{owner}/{repo}/pulls/{pr}/reviews?per_page=100'` (fields `id`, `user.login`, `commit_id`, `html_url`, `body`). Judge each item against the current code, as you would a thread. With no thread to reply to or resolve, a review's items are answered by one PR comment of ours that starts with `Re: <review html_url>`; a review with body items and no such comment is still open.

## A green bot is one that reviewed the head

A review bot's green check counts only once that bot has reviewed the current head: a review whose `commit_id` is the head SHA, or the bot's own summary naming the head commit. A bot that is rate-limited, paused, skipping the PR for size, or only reviews when tagged still reports green. Re-trigger it once with its tag (`@coderabbitai review`, `@greptileai`), after its rate limit resets when it names a reset before its deadline, and give it until its deadline (**Waits**); if it still hasn't reviewed the head, report it as `NOT_REVIEWED=<bot>:<reason>` instead of counting it green. A bot the repo's `docs/agents/review-bots.md` says not to re-trigger counts only when it reviewed the head on its own: it is never tagged or waited for, a head it skipped is reported `NOT_REVIEWED=<bot>:<the reason review-bots.md gives>`, and findings it posts later are worked like any other.

## The final pass

A repo can name **final-pass reviewers** in `docs/agents/review-bots.md`, each with the tag that requests it: bots billed per review, so whether to request one is your **call**, made after the other reviewers have converged and taken the easy findings. A final-pass reviewer's tag comments on the PR are the record of its requests: read the PR's comments for them before each call below, which applies to each final-pass reviewer on its own.

- **A request earns its cost** when the code it would review carries **residual risk**: new behaviour that tests and the other reviewers can pass while an ordering of events, an edge input or an error path the tests never exercise still breaks it. State kept across events, concurrent writers, cleanup and deletion, permissions and tokens, and input limits carry it, in code, config and CI workflows alike; so do agent instructions that decide when a loop re-enters, counts or stops, however short. Size counts where it hides paths: a change too large for you to trace every path through earns a request without a named risk. A change is **mechanical** when every hunk is copy, prose no agent follows, a rename, a move, a generated file or a style tweak to an existing element: it fails loudly and cheaply, and merges on the other reviewers' word. A repo that names several says in its doc which suits which risk.
- **Make the call when a standalone run converges, or at `/pr-loop` step 7,** for each reviewer not reported `NOT_REVIEWED` on this PR whose tag comment or logged skip doesn't already cover the head. For one with no request yet, judge the whole PR; for one that has reviewed, judge only the **unreviewed delta**, the changes since its last review, by the behaviour it adds wherever it sits. A fix that only corrects what a finding named, a merge of the base branch that resolves no conflicts, and a reply to a rejected finding are skips; a merge that resolves conflicts is judged on its resolutions alone. Standalone, post every request you make, each as its own comment; under `/pr-loop`, step 8 posts them. The re-trigger above passes final-pass reviewers over.
- **Log each call** as a decision-log row (`phase pr-comments`, `source me`, `asked no`, `result accepted`): requested or skipped, the risk that decided it, and the head it covers.
- **Before a request, and after a logged skip,** each pass leaves it out of step 1's green gate, step 6's wait and the check on who has reviewed the head.
- **After a request,** it gates convergence until it reports a review that started after that tag comment: a review, or a comment or check-run summary saying the review finished; a check's state alone doesn't show that. A skip the reviewer itself reports (for cost, size or usage), or its deadline passing with no review (**Waits**), ends the wait as `NOT_REVIEWED=<bot>:<reason>` rather than a loop failure. Once it has reviewed or been reported `NOT_REVIEWED` since its latest request, its check on any later commit, even one still pending, drops out of step 1's green gate and step 6's wait. The repo doc says how to read its review and its skips, and what it posts when it finishes, since a T3 watch wakes on comments and reviews, not on a passing check.
- **Its findings** are worked like any other, once every requested final-pass reviewer has reviewed or been reported `NOT_REVIEWED`: a push before then cancels a review still running.
- **It's done** in either case: it has been reported `NOT_REVIEWED`; or its call on the head is logged, every finding from its reviews is fixed or answered, and, if that call was a request, the review it asked for has landed. Its report is `passed on <sha>`, naming the head its last review covered, or `skipped: <why>` when it was never requested.

## Waits

Every wait names its **deadline** and a **wake source** that fires by then; a turn ends on a wait only once that wake source is set.

- **Wake sources.** A PR watch fires on PR events (a comment, a review, a push), never on the clock. A clock time (a deadline a reviewer may never answer by, or a named rate-limit reset to re-trigger a bot at) needs a timer: in T3, a one-time `schedule_task` bound to this thread; in a native CLI, the poll in step 6, run in the foreground; in Claude Code a background command that exits at that time also wakes the turn. A timer whose wait ends another way is deleted (`delete_scheduled_task` in T3).
- **Deadlines.** A review bot's is 30 minutes from the later of its latest request and the push, and a check's 30 minutes from the start of the CI run awaited (the push, or a re-run), unless the repo names a longer one for it: in `docs/agents/review-bots.md` for a bot, or as a line `- deadline: <check> = <minutes> min` in `docs/agents/pr-loop.md` for a check. A `/codexloop` round follows its own limit (its **Reviewer** section); any other wait, such as a delegated child, names its deadline when it starts.
- **At the deadline,** a review bot still silent is reported `NOT_REVIEWED=<bot>:<reason>`, the reason naming how long it waited (`silent 30 min`); it drops out of step 1's green gate and step 6's wait on this head, and the loop carries on, reporting the missing review rather than counting it clean. A bot whose rate limit resets after its deadline is reported the same way with the reset time, and not re-triggered on this head. A check still pending is reported `PENDING=<check>:<minutes> min` and likewise drops out of the gate and the wait on this head; it is never counted green. Any other wait reports what is still running and for how long, and the run carries on without it.

## Each pass

1. **Fetch & converge.** Find the PR (`gh-axi pr view` off the current branch, or `<pr>` if given). Read review comments and their thread resolution (`gh-axi pr view <pr> --comments --reviews`; `api POST /graphql` for each thread's `isResolved`), and reviewer states (`gh-axi pr checks <pr>`). For an unresolved thread whose last comment is already our reply (an earlier pass stopped before resolving it), resolve it when the reply is a rejection or the commit it names is on the remote branch (`git fetch origin <branch>`, then `git merge-base --is-ancestor <sha> origin/<branch>`); otherwise work it again. Keep the unresolved threads whose last comment is someone else's, including a bot answering our reply, and the open review-body items (see **Review-body items**). **Converged** when no unresolved thread or open review-body item remains AND every reviewer is green (`SUCCESS`; `NEUTRAL`/`SKIPPED` pass; `FAILURE`/`CANCELLED`/`TIMED_OUT` don't) AND every review bot has reviewed the head or been reported `NOT_REVIEWED` (see **A green bot is one that reviewed the head**; a final-pass reviewer follows **The final pass**; a check reported `PENDING` is out of the gate, **Waits**). On convergence, a standalone run makes its final-pass calls; one that posts a request continues at step 6, or stops there under `--once`; otherwise emit `LOOP_STATUS=CLEAN ITERATIONS=<N> [NOT_REVIEWED=<bot>:<reason>,…] [PENDING=<check>:<minutes> min,…] [FINAL_PASS=<bot>:<its report>,…]` and stop. A red reviewer with no comment is still a finding — investigate and fix it.

2. **Partition into clusters.** Holding every comment at once, group them: comments on the same code or that reference each other share a cluster; everything else is a cluster of one. This call is yours to make directly from full context — no line-distance heuristic.

3. **Fan out.** Handle dependent clusters serially. For independent clusters, use a bounded handful of subagents with isolated worktrees for writes, or fix them serially in the parent when isolation is unavailable. Each fixer has this task:
   > Address these PR comments: {cluster}. Read the code around each. Judge whether each raises a real issue — technically correct, an actual improvement to quality/security/maintainability, consistent with the codebase. A fix that adds a mechanism must pass the mechanism rule in `~/.claude/skills/recap-pr/LEDGER.md`; one that fails it is not a valid fix. Fix the valid ones in your isolated worktree; for invalid ones, prepare a respectful explanation of why it isn't one. Commit only your assigned fixes and return the base SHA and commit SHA. Do NOT push, reply, or resolve. Return per comment: `valid` (bool), `action` ("Fixed: …" / "Not an issue: …"), `files` (paths changed), `reply` (message to post).

   Judge every finding on its merits, CodeRabbit's "Nitpick" items included: fix a valid one when the fix is cheap, reject bikeshedding and bloated defensive code, and never fabricate a fix just to silence a bot.

4. **Finalize (parent only).** Collect results and review each fixer's diff against its returned base. Cherry-pick accepted fixer commits into the parent branch one at a time; resolve conflicts in the parent and run the combined affected checks. Record the source-to-parent SHA mapping for each fix. When isolation is unavailable, the parent makes the edits serially. A fix is not complete while its only copy remains in a child worktree. Check every returned fix that adds a mechanism against the mechanism rule in `~/.claude/skills/recap-pr/LEDGER.md`; revert one that fails and rewrite its reply as a rejection. Print a table (Comment | File | Valid? | Action). Commit any remaining parent edits with a message naming the count addressed and push all accepted fixes (step 5's rules) before replying, so every "Fixed" reply names a commit already on the remote. Under `/pr-loop`, run its pass sequence on these commits instead of pushing (it pushes once the check allows it), then recheck each fix and its reply against the pushed head. Then reply to each comment (a fix's reply names the pushed parent-branch SHA that contains it, rather than an unpushed fixer SHA) and resolve its thread via `gh-axi api` (`POST /repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`, and the `resolveReviewThread` graphql mutation). Answer each review's body items with one PR comment starting `Re: <review html_url>` that lists every item with its outcome and pushed SHA; pass bodies through `--body-file` so backticks survive. Log each comment and review-body item as one decision-log row (`phase pr-comments`, `source bot:<reviewer>`, `asked no`).

   Once each fixer has finished and its accepted fixes are pushed, use `~/.agents/skills/cleanup/SKILL.md` to retire its eligible workflow-owned temporary worktree during this pass. Preserve its branch unless deletion was separately authorized, and record any retention reason. Rejected fixer work follows the same preservation and ownership checks.


**If `--once`: stop here.**

## Loop

5. **Push rules** (the push itself happens in step 4) — never force-push; never push to `master`/`main`. If the remote diverged, stop with `LOOP_STATUS=FAIL ERROR="remote diverged"`.

6. **Let reviewers re-review.** In T3, use its injected PR-watch workflow, set the timers **Waits** names, and end the turn. In a native CLI, poll `gh-axi pr checks <pr>` every 60–120s until every reviewer reaches a final state — ignore deploys, pending or red — and each awaited bot has reviewed the head (**A green bot**), or until the earliest deadline or named reset **Waits** sets. Once they settle, wait ~45s for bots to post. A reviewer still pending at its deadline is handled as **Waits** says.

7. **Repeat** from step 1 — its convergence test decides when to stop. **No iteration cap**: a PR can take 20–30+ passes to settle, so print the pass count and remaining items each round for interruptibility. **No-progress guard:** track addressed comment IDs and review-body items (review ID plus file:line) across passes in `/tmp/address-pr-comments-history.txt`; if one ID is re-flagged 3 passes running with no fix landing, stop with `LOOP_STATUS=FAIL ERROR="no progress on comment <id>"`.
