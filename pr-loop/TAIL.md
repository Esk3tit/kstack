# The tail

Read this at SKILL.md's step 6, which runs the three parts below on one head together, and when step 7 runs the passes its check names.

## Standards and Spec

Run `/code-review` for the axes on `log.sh --check`'s closing line (skip it when that names neither), with the fixed point `origin/<base>` (the branch it merges into), the spec given up front (the ticket if any, and the user's settled decisions, `log.sh --pins`, which carry the start's request), and `spec-body-<head>.md` beside the log named as the file it saves the PR body to (on every Spec run, step 7's too). Before each Spec run, compare the live body with the last body Spec saved and restore only what a bot wrote back over it, as `/pr`'s **Editing the body** says, keeping a person's change. Fix every hard violation and every spec gap; take a judgement call only when it makes the change simpler or clearer. Log each finding with its outcome, and record each axis that ran on the head it reviewed: `log.sh --pass standards <head> clean|fixed`, and `log.sh --pass spec <head> clean|fixed [<body file>]`, giving that file when Spec read it.

## Fable

Fable's call is made, and acted on, once on each head the tail runs on: it runs when the changes since the last head it reviewed (`last read` in the check; the whole PR if none) carry new judgement: a design or behaviour change its users or agents will feel, a call the mechanical reviews keep circling, or coupling a reviewer has to hold in their head. Changes that only carry out findings already settled, and mechanical edits, go without it. Log the call and its reason either way, and when it runs, follow [FABLE.md](FABLE.md). Its record never gates merge-ready.

## The final pass

A repo can name **final-pass reviewers** in `docs/agents/review-bots.md`, each with the tag that requests it: bots billed per review, so whether to request one is your **call**. A final-pass reviewer's tag comments on the PR are the record of its requests: read the PR's comments for them before each call below, which applies to each final-pass reviewer on its own.

- **A request earns its cost** when the code it would review carries **residual risk**: new behaviour that tests and the other reviewers can pass while an ordering of events, an edge input or an error path the tests never exercise still breaks it. State kept across events, concurrent writers, cleanup and deletion, permissions and tokens, and input limits carry it, in code, config and CI workflows alike; so do agent instructions that decide when a loop re-enters, counts or stops, however short. Size counts where it hides paths: a change too large for you to trace every path through earns a request without a named risk. A change is **mechanical** when every hunk is copy, prose no agent follows, a rename, a move, a generated file or a style tweak to an existing element: it fails loudly and cheaply, and merges on the other reviewers' word. A repo that names several says in its doc which suits which risk.
- **Make the call on each head the tail runs on** for each reviewer not reported `NOT_REVIEWED` on this PR whose tag comment or logged skip doesn't already cover the head, posting the requests you make at the same time, each as its own comment. For one with no request yet, judge the whole PR; for one that has reviewed, judge only the **unreviewed delta**, the changes since its last review, by the behaviour it adds wherever it sits. A fix that only corrects what a finding named, a merge of the base branch that resolves no conflicts, and a reply to a rejected finding are skips; a merge that resolves conflicts is judged on its resolutions alone. Once Bugbot has been requested on this PR, any unreviewed delta earns a request, and only its tag comment covers a head, never a logged skip.
- **Log each call** as a decision-log row (`phase pr-comments`, `source me`, `asked no`, `result accepted`): requested or skipped, the risk that decided it, and the head it covers.
- **Before a request, and after a logged skip,** each COMMENTS.md pass leaves it out of its green gate (step 1), its wait (step 5) and the check on who has reviewed the head.
- **After a request,** it gates convergence until it reports a review that started after that tag comment: a review, or a comment or check-run summary saying the review finished; a check's state alone doesn't show that. A skip the reviewer itself reports (for cost, size or usage), or its deadline passing with no review (COMMENTS.md, **Waits**), ends the wait as `NOT_REVIEWED=<bot>:<reason>` rather than a loop failure. Once it has reviewed or been reported `NOT_REVIEWED` since its latest request, its check on any later commit, even one still pending, drops out of COMMENTS.md's green gate and wait. The repo doc says how to read its review and its skips, and what it posts when it finishes, since a T3 watch wakes on comments and reviews, not on a passing check.
- **Its findings** are worked like any other, once every requested final-pass reviewer has reviewed or been reported `NOT_REVIEWED`: a push before then cancels a review still running.
- **It's done** in either case: it has been reported `NOT_REVIEWED`; or its call on the head is logged, every finding from its reviews is fixed or answered, and, if that call was a request, the review it asked for has landed. Its report is `passed on <sha>`, naming the head its last review covered, or `skipped: <why>` when it was never requested.
